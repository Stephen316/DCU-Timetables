# Architecture

## Layers

The app is layered so the one fragile part — the unofficial DCU data source — is
isolated behind a protocol and everything above it is pure and testable.

```
┌─────────────────────────────────────────────┐
│ App        DCUTimetableApp, RootView         │  entry / shell
├─────────────────────────────────────────────┤
│ Features   Onboarding, Week/Day views        │  SwiftUI + view models
├─────────────────────────────────────────────┤
│ Data       TimetableSource (protocol)        │  I/O boundary
│            ├─ DCUAPIClient  (+ DTOs, mapper) │  live JSON API
│            ├─ (planned) ICalSource           │  fallback
│            └─ TimetableCache                  │  offline (Codable on disk)
├─────────────────────────────────────────────┤
│ Core       models, ActivityCode, ClashDetector,   pure, no I/O, no SwiftUI
│            WeekCalendar                        │
└─────────────────────────────────────────────┘
```

### Core (pure)

No networking, no SwiftUI, no Foundation URL types beyond `Date`. Fully unit-testable
off-device and portable (e.g. to Android/Kotlin later).

- `TimetableEvent` — one class: module, activity, start/end, rooms, group, staff, weeks.
- `EventType` — `.onCampus`, `.synchronous`, `.asynchronous`, `.booking`, `.unknown`.
- `ActivityCode` — parses `BIO1000[1]OC/L1/01 Surname A - M` into module code,
  occurrence, activity kind (`L`/`T`/`P`…), group number, and cohort label. This is how
  a student's *group* is identified for filtering and clash detection.
- `Programme` / `TimetableCategory` — a searchable timetable object + its identity.
- `TeachingWeek` / `WeekCalendar` — the API's week→date mapping.
- `ClashDetector` — pure function: given events, return overlapping pairs.

### Data (I/O boundary)

- `TimetableSource` — the protocol the app depends on:
  ```swift
  protocol TimetableSource {
      func searchProgrammes(query: String) async throws -> [TimetableCategory]
      func weekCalendar() async throws -> WeekCalendar
      func events(for category: CategoryRef, weeks: [TeachingWeek]) async throws -> [TimetableEvent]
  }
  ```
- `DCUAPIClient` — the live implementation. Codable DTOs mirror the API responses;
  `EventMapper` converts DTOs → Core domain. All requests carry `Authorization: Anonymous`
  and send the **complete `ViewOptions`** (see API landmine).
- `TimetableCache` — persists the last-fetched events + fetch timestamp as JSON on disk,
  so the app is offline-first and can show staleness.

### Features (SwiftUI)

Thin views over view models that call a `TimetableSource`. No view talks to the network
or parses JSON directly.

- `ProgrammePickerView` — search + pick programme (and later, group).
- `WeekView` / `WeekViewModel` — fetch + render the week, surface clashes and staleness.

## Data flow (happy path)

```
onboarding → searchProgrammes(query) ──► pick programme + group ──► persist selection
week view  → weekCalendar() + events(for:weeks:) ──► TimetableCache (write)
             │
             └─ offline: read TimetableCache first, refresh in background
render     → filter events to chosen group ──► ClashDetector ──► WeekView
```

## Why a protocol seam

The DCU API is unofficial: it has already migrated hosts once
(`opentimetable.dcu.ie` → `mytimetable.dcu.ie`) and its API host is a versioned string.
Keeping every screen behind `TimetableSource` means a break is contained to one file, and
the planned iCal fallback (or a future backend proxy) drops in without touching Core,
cache, or UI.

## Conventions

- **Core is dependency-free and pure.** If it needs `URLSession`, it belongs in Data.
- **Unset values render as `--`, never `0`.**
- **Tests are Swift Testing** (`@Test` / `#expect`), with recorded JSON fixtures for the
  API format so a DCU-side change fails a test rather than shipping silently.
- The `.xcodeproj` is generated by XcodeGen from `project.yml` and is gitignored.
